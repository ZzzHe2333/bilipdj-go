## 风险与建议优先级

1. **P0：B站真实连接**。用户现场报告 `WSS :2245` 鉴权后 EOF；本版改用 `buvid`、同会话 Cookie、现代鉴权元数据，并展示服务端关闭码。离线无法证明已恢复，务必先做真人直播间验证。
2. **P0：旧配置导入安全**。导入前备份并保证预览无副作用；敏感 Cookie 不经管理 GET API 返回；ZIP 路径/体积有限制；仍需覆盖旧版不同版本 YAML。
3. **P1：权限模型**。本版已有可信房管/主播弹幕角色与管理员分层，**但按昵称配置最高管理员的兼容行为存在冒名风险**。礼物事件基础链已迁移，但仅在已连接的 B站流中受信任，且尚未进行真实礼物实机验收，禁止宣称权限完全对等。
4. **P1：OBS 和第三方 API**。SSE 不等同旧版 WebSocket 协议，所有依赖旧 `/ws` 的程序需适配。
5. **P2：高级服务**。礼物资格已增加基础链；WebDAV、插件、扫码登录、增量更新仍待迁移。


## v0.6.0 新增离线审计用例

- 每日限额：取消后重复入队拒绝、跨重启保留、04:00 边界重置、抖音和 B站身份隔离。
- 权限：普通观众/普通管理员不能添加管理员，最高管理员可操作；房管开关关闭时不得管理，开启后可管理；黑名单清除管理身份并拦截命令。

- **验证范围：** Go 单测/竞态测试与静态检查。没有真实 B站直播间鉴权通过的证明；本地测试结果不能替代线上验证。

## v0.6.0 B站全节点鉴权 EOF 回归

用户反馈所有 WSS `:2245`、TCP `:2243` 节点均在 op=8 之前断开。已对比旧版 `resolve_bilibili_login()`：v0.4.x **即使传递已登录 Cookie 仍始终认证 uid=0**。v0.6.0 的 `biliDiscovery` 携带与 token 获取所用 Cookie 相同的登录 UID；优先使用 `nav.isLogin=true` 的 `mid`，明确未登录时不使用旧 Cookie 中的 UID。消息仍只能在 op=8/code=0 后置为已连接，保留 WSS/TCP 双通道回退和关闭原因记录。

**验证范围：** 单测包括同会话 UID+token、过期 Cookie、WSS 封包和 0x08 鉴权确认；未在用户环境或公网 B站实际服务端复验。UID 不一致是已证实的软件缺陷，但不足以证明是所有 EOF 的唯一原因。

## v0.6.1 B站扫码确认后 Cookie 丢失修复

用户实测：**手动配置 Cookie 后 B站弹幕流正常**，说明先前鉴权 EOF 在该登录条件下已解决；但 v0.6.0 手机扫码确认后报「不受信任的跳转地址」。根因是回调合法性校验只接受 `*.bilibili.com`，排除了 B站 QR 成功响应中的官方 `passport.biligame.com`。同时 2026 年新增 `crossDomain?ticket=...` 格式，必须请求票据回调并从首跳 HTTP 302 `Set-Cookie` 取回 SESSDATA 等 Cookie。

本版限定官方 HTTPS 回调域名与固定路径，禁止自动跟随恶意跳转；兼容旧版查询字符串凭据与新版票据。仅 `nav` 返回 `isLogin` 与有效 `mid` 后落盘；扫码失败时维持旧 Cookie，不改动当前正常的弹幕接收协议。测试覆盖旧 URL、新 ticket/302、多域名拦截、外部重定向拒绝以及成功保存。**真实 B站扫码端到端仍需要用户实际验证。**
