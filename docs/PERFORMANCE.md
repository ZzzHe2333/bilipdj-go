# BiliPDJ Go 性能监测

主控制台左侧新增「性能监测」。默认间隔 **2 秒**，允许设为 **0（关闭）或 1–1200 秒**。离开页面或标签页隐藏时停止采样；返回页面恢复。间隔保存在当前浏览器中，不写入直播存档。

## 不等距滑杆

进度条四个标签依次是 0、12、120、1200；第一段以 1–12 秒为精细区间，第二段覆盖 12–120 秒，第三段覆盖 120–1200 秒；各约占进度条三分之一。设为 0 完全不请求采样。可在数字输入框设定任意 1–1200 秒整数。

## 数据口径与操作系统支持

| 指标 | Windows | Linux | macOS |
|---|---|---|---|
| 本进程 CPU | GetProcessTimes | getrusage | getrusage |
| 整机 CPU | GetSystemTimes | /proc/stat | 暂不支持 |
| 内存 | 当前 Working Set | 当前 VmRSS | 峰值 RSS，必要时 Go 堆占用替代 |
| 数据目录大小 | 每 60 秒有界扫描一次 | 相同 | 相同 |
| 进程 I/O | GetProcessIoCounters 读写字节 | /proc/self/io 物理层读写字节 | 暂不支持 |
| 网络接收/发送 | GetIfTable **整机接口** | /proc/net/dev **整机/容器网络接口** | 暂不支持 |
| GPU、NPU | 暂无可信进程级读数 | 暂无可信进程级读数 | 暂无可信进程级读数 |

网络不是 BiliPDJ 的独占用量，也包含其他软件流量。Windows 网卡数据使用 32 位累计计数器，数值回绕时不会伪报负流量。Windows GetProcessIoCounters 可能包含缓存文件或设备 I/O，并不代表物理磁盘吞吐；macOS 的峰值 RSS 不代表实时 RSS。所有无法测量的指标显示「不可用」，与真实 0% 明确区分。

进程 CPU 是本项目累计 CPU 时间占全部逻辑处理器时间的比例。CPU、磁盘、网络速率都需要两个采样点，第一帧只建立基线。数据目录递归扫描最多处理 10000 个条目或 150ms，超过即放弃，最大每分钟执行一次。

## 安全和资源占用

- GET /api/performance 仅允许原有管理员鉴权通过的调用；不返回敏感令牌、磁盘绝对路径。
- 服务端不启动后台监控循环；在用户打开页面、间隔大于 0 且标签页可见时才响应前端采样。
- 监测本身占用少量资源；直播高负载时建议设置 12s 或 120s，也可设置 0 停止。
- 此页面不会改变排队存档、多平台直播监听和 OBS 来源。

## 与 Python Windows 版的对比

Python apps/windows/performance_monitor.py 采用 psutil，提供**整机 CPU**、进程 RSS、系统内存使用率和程序目录大小（目录启动后读一次）。默认**关闭**、开启后默认 2s，输入范围 0.5–60s。没有进程 CPU、网络速率、进程磁盘读写和 NPU/GPU 读取。

Go 版提供项目进程 CPU、可用的整机 CPU、进程内存、数据目录缓存占用、Windows/Linux 进程 I/O 与注明范围的整机/容器网络流量。默认间隔 2s，支持 0 完全关闭及 1–1200s、非线性滑杆和手动输入，切页即停。GPU/NPU 目前仍明确不可用，**不代表已实现 NPU 设备利用率统计**。

Python Web 的 apps/web/static/performance.js 是 OBS 前端增量渲染与滚动 FPS 优化，并非硬件资源监测。
