# 弹幕与导入事务、黑名单及 Cookie 并发修复

## 修复项目

1. **弹幕变更仅在持久化成功后生效**：新增完整直播状态快照，包含当前队列、全部 10 个槽位、配置/管理员权限、每日排队次数、礼物积分与去重记录以及样式。执行 `OnDanmu` 排队/管理命令前先建立快照；`saveLocked()` 失败时恢复内存与 Windows Local 独立队列文件，且不再对外发送成功的 `queue` 事件。原始弹幕日志仍保留，失败时发送警告事件。管理员开关、每日排队限制、礼物积分消耗都一起回滚。
2. **礼物奖励的事务与黑名单**：B站礼物事件同样先持久化，成功后才发布礼物积分结果；如发生磁盘写入异常，恢复礼物积分、已处理礼物的去重 ID 和 Local 队列。统一调用 `isBlacklisted()`，同时识别新权限表中的 B站/两平台封禁及历史 UserID 黑名单。
3. **主控制台跨页面切槽**：主控制台刷新由分别读取 `/api/queue` 与 `/api/queue/slots` 改为带 `active_slot` 的 `/api/queue/state` 快照与槽位概览；若两次读取期间存档切换，等待后重新获取。通过请求序列号防止旧刷新结果覆盖新列表。SSE 的队列变化只触发刷新，不再用缺少槽位号的事件数据直接覆盖成员数组。
4. **Python 存档导入回滚**：导入前保存整套直播状态快照，包括 Local 文件对应的队列槽位；如果写 Roaming 状态失败，恢复配置/每日次数/内存队列并重新写入旧 Local 独立队列文件。如果回滚也失败则返回明确错误。导入成功后的监听重建在同一 App 锁内完成，不留重建旧配置的竞态窗口。
5. **扫码 Cookie 并发保存保护**：`POST /api/config` 对省略或已脱敏的 Cookie 使用“保留最新服务端凭据”语义。正式提交前必须持有 App 锁并再次合并当前全部平台 Cookie、按 ID 的额外 B站/抖音 Cookie；再校验多房间/会话冲突。两个阶段之间的扫码登录/注销不会被旧的配置表单恢复。管理员明确提供的非空 Cookie 仍可主动覆盖凭据。

## 数据与部署兼容

- 不更改 VERSION、不发布 Release；本次修改合并后只有下一次明确的发布才会进入发行包。
- 不迁移或删除已有存档；旧版管理 API 与多直播间数据结构不变。
- 正常文件写入失败可以回滚；突然断电、磁盘永久故障或回滚本身再次失败时，无法跨多个独立文件保证强原子性，请保留备份。
- 本次自动测试并不能替代真实 Windows OBS、B站/抖音扫码与高并发直播实机验收。
