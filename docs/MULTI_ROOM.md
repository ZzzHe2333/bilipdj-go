# 多直播间同时监听与多 B站 Cookie

BiliPDJ-Go 可为 Bilibili、抖音分别添加多个直播间，所有实例仍使用当前 Go 队列及选中的十个存档槽位，不按直播间拆分队列或创建隐藏存档。

## Web 操作

进入 **平台与规则**，使用原来的 B站/抖音配置作为第一个房间。在下方「更多直播间」处点击 **＋ 添加 B站直播间** 或 **＋ 添加抖音直播间**；每个房间具有独立直播间号/链接、启用开关、Cookie 输入框与连接状态。

1. 新增 B站房间先保持关闭，填写房间号，点击**保存并重新连接**（让系统保存房间 ID）。
2. 点击该房间的 **此房间扫码登录**，用相应 B站账号在手机端扫码确认。或者在该房间高级设置中手动输入专用 Cookie（必须含 `SESSDATA`）。
3. 系统将 Cookie 保存到该房间；开启该房间并点击保存。其他 B站房间不会继承它的 Cookie。
4. 多个抖音房间各自填写直播间号或 `live.douyin.com` 网址，通常无需 Cookie，独立启用后可与 B站同时监听。
5. 「移除」只是前端标记，按「保存并重新连接」后才删除房间配置并取消其监听；删除时相应的 Cookie 一并删除。

支持最多 **30 个额外房间**（首个 B站和首个抖音不算在内）。实际允许多少个同时在线取决于直播平台连接策略、网络、主机性能及 Cookie 的有效性，不保证平台一定接受大量并行连接。

## B站强制一对一规则

- **同时启用两个及以上 B站房间时，每个房间必须持有自己的 Cookie**，且必须含 `SESSDATA`。没有 Cookie 就会拒绝保存配置。
- 同一 `SESSDATA` 不允许同时绑定到多个已填写房间号的 B站实例；重复的房间监听也会被拒绝。前者检查已保存 Cookie 的会话标记，后者避免同一房间重复收集弹幕。
- 可以逐个扫码或分别手动粘贴 Cookie。扫码会话有目标房间 ID，扫码完成只保存该实例的 Cookie，不会覆盖旧主房间。
- 点击某一房间「清除本房间登录」只删除该房间 Cookie 并停用该房间，其他监听继续存在。
- 本地格式校验不能证明 Cookie 永久有效：登录状态由直播平台实际握手验证，过期请重新扫码。
- 即使一个 B站账号登录产生多个不同的会话，平台仍可能在服务端限制并行登录；不要把本地静态校验理解成绕过平台的权限检查。

## 状态、排队和身份隔离

每个监听实例拥有稳定 `id`、独立的 goroutine/context、单独的连接状态和日志标签，例如 `bilibili-mroom001`。各监听来源保留真实平台名 `bilibili` / `douyin`，附带非敏感的 `instance_id` 用于运维排查。

**排队去重仍按平台 + 用户 ID**，不是按实例 ID。因此，同一 B站用户在两个 B站直播间发送“排队”，通常只会入队一次；同一个 ID 的 B站和抖音属于不同平台身份，按原权限规则处理。所有直播间共享队列存档，切换槽位也不创建额外隐藏副本。

## 与旧版本兼容

旧版 `config.bilibili`、`config.douyin` 仍作为两个平台的**主实例**（ID 分别为 `bilibili` 和 `douyin`）；已有房间号、Cookie、弹幕配置和队列存档无需迁移。新加的房间仅存入 `config.listeners` 列表，旧版程序不具备识别这些额外配置的能力。降级前建议完整备份用户数据。

## Cookie 安全

- Cookie 只持久化到本机用户数据文件；API `GET /api/config` 不会回传任何 Cookie 原文，只以 `cookie_configured`（主实例）和 `listener_cookies`（额外实例）标注布尔状态。
- `POST /api/config` 必须通过管理员/本机访问校验；空 Cookie 表示沿用**同 ID**下已保存的 Cookie，不会因列表排序/删除错配到其他房间。
- 对多份 Cookie 的请求提高到有界 **512 KiB**，其他管理接口仍维持原来的 16 KiB 限制。
- 请勿把状态文件、手动输入的 Cookie、`SESSDATA` 或扫码回调地址上传至公开 Issues；Windows/Linux/macOS 中保存的文件应只允许当前用户访问。
